## 2. Чинить в первую очередь

### 2.1 «Без заливки» из тулбара не подсвечивает меню
Проверено запуском (headless-проба, тулбар создаётся первым, как в
`Controller:38`): NPE **нет** — в `SwitchFill` защита `if (fillItem != null)`
срабатывает, хотя `fillItem`/`noFillItem` в момент `createToolBar()` ещё `null`.
Функционально всё в порядке, но это хрупкая «нулевая защита»: порядок создания
тулбара и меню случайно совпал с порядком, на который она рассчитана.
Достаточно переставить `Controller:37` и `Controller:38` местами
(меню раньше тулбара) — и защита перестанет работать.

**Как чинить (надёжно):** `MenuCreator` должен передавать в команду себя
(`SwitchFill` спрашивает `menuCreator.isReady()`), либо строить меню до
тулбара — тогда null-проверки уходят вовсе.

### 2.2 Одна `FillBehavior` «рисует» сразу все фигуры
`ShapeType.createShape()` передаёт *новый* `MyShape`, но `ShapeState` не
хранит поведение, а `MyShape` хранит — хорошо. Проблема в `MyShape:43-47`:
`setFb()` мутирует переданную стратегию (`setShape`, `setColor`) — если один
и тот же объект `NoFill` попадёт в две фигуры, они начнут рисовать друг друга.
Сейчас спасает только то, что `ShapeFactory.createShape` всегда создаёт `new Fill()/new NoFill()`.

**Как чинить:** сделать `FillBehavior` иммутабельным —
`MyShape(color, shape, fb)` вообще не должен вызывать `fb.setShape(...)`,
а `draw(Graphics2D g, Shape s, Color c)` должен получать фигуру аргументом.

### 2.3 Двойное выделение в меню «Фигура»
`MenuCreator:141` и `:146`: у «Прямоугольник» **и** у «Эллипс» стоит
`setSelected(true)`. В `ButtonGroup` это гарантированный баг: пользователь
увидит два «нажатых» пункта.

**Как чинить:** у эллипса `new JRadioButtonMenuItem("Эллипс", false)`.

### 2.4 Действие «Рисовать» создаёт вторую фигуру
`Controller.switchActionDraw()` → `new ActionDraw(...)` → конструктор делает
`model.setDrawableShape(shapeFactory.createShape(shapeState))`, то есть
добавляет в модель фигуру-призрак **до** нажатия мыши. После двух кликов по
«Рисовать» на холсте появятся пустые (0×0) прямоугольники.

**Как чинить:** убрать создание фигуры из конструктора, делать её только в
`mousePressed`.

### 2.5 `setShapeList` ломает инкапсуляцию
`Model.setShapeList(List<MyShape>)` присваивает внешний список. Модель может
заполнить кто угодно снаружи. Лучше заменить на `clear()` / `getShapes()` в
виде неизменяемой вьюхи (`Collections.unmodifiableList`).

## 4. Что добавить — по возрастанию сложности

### Уровень A. Обязательный минимум (1–2 вечера)

1. **Иконки в `resources/ico`** — снимает пустые кнопки.
2. **Undo / Redo (Ctrl+Z / Ctrl+Y).** Самая ожидаемая функция и самый
   дешёвый способ показать знание паттернов. Два варианта:
   * *Command-based*: `AppCommand` уже есть — добавить `DrawShapeCommand`,
     `ClearCommand`, стек выполненных/отменённых. Естественное продолжение.
   * *Memento*: `Model` умеет `snapshot()` → `List<MyShape>` deep copy.
   Рекомендую command-based — он семантичнее и ложится на существующую архитектуру.
3. **Кнопка «Очистить всё»** + подтверждение через `JOptionPane`.
4. **`application` плагин** в `build.gradle`:
   ```groovy
   plugins { id 'application' }
   application { mainClass = 'org.example.BootClass' }
   ```
5. **Тесты (JUnit 5)** на модель — их легко писать, и они сильно поднимают оценку:
   * `ShapeFactoryTest` — фабрика возвращает правильный тип фигуры;
   * `FillNoFillTest` — `Fill`/`NoFill` рисуют без NPE на пустой фигуре;
   * `ShapeStateTest` — дефолты при `null` (там уже есть `requireNonNullElse`);
   * `ModelTest` — `addShape` уведомляет наблюдателя.

### Уровень B. Функциональность редактора (по приоритету)

6. **Выделение и перетаскивание фигур** (паттерн Strategy, вторая стратегия
   рядом с `ActionDraw`):
   * `AppAction` → `ActionSelect`; `Controller` держит список действий и
     переключает текущее по меню «Действие» (пункт уже создан, но умеет только `ActionDraw`);
   * хит-тест `shape.contains(point)`, иначе фигуры не выбрать;
   * инвариант: в `Controller` один `currentAction`, но много реализаций —
     это классический пример Strategy в терминах лекции.
7. **Удаление выделенного (Delete)** — командой, чтобы сразу попасть в undo-стек.
8. **Толщина линии и стиль обводки** — `BasicStroke` в `FillBehavior`/`NoFill`.
9. **Слой/порядок z-order**: «на передний план» / «на задний» — просто
   перестановка в `shapeList`, хороший пример работы с `ArrayList`.
10. **Файлы: сохранение и загрузка (JSON).** Без внешних библиотек —
    написать свой мини-сериализатор фигур или подключить Gson. Модель уже
    отделена от Swing, поэтому это чистый повторяемый код.
11. **Экспорт в PNG** через `BufferedImage` + `ImageIO.write`.
12. **Сетка и «прилипание» к сетке** — `pixelSnap(point, 10)`.

### Уровень C. «На отлично» — то, что делает проект интереснее всего

13. **Поворот фигур через `AffineTransform`.** Требует отказаться от
    `RectangularShape` в пользу `Shape` — заодно устраняет все проблемы из п. 2.2.
    Кандидат на отдельный раздел в пояснительной записке.
14. **Слои и композиция (`Composite`).** Группа фигур = одна фигура
    (паттерн Composite) — сразу дают работу «выделить рамкой группу и перетащить».
15. **Кривые Безье (перо).** `Path2D` + `CubicCurve2D`, 4 контрольные точки.
16. **Мультидокументность (вкладки `JTabbedPane`).** Показывает, что модель
    действительно отделена от view: два `Model` + два `MyPanel`.
17. **`java.util.Observable` → свой `PropertyChangeListener`/событийная модель.**
    Устраняет deprecated API и все warnings — `-Xlint:all` должен стать чистым.
18. **Паттерн «Мементо» + собственный формат `.paint`** (версия, дата, список фигур)
    вместо сырого JSON — академично и логично рядом с undo.
19. **CI (GitHub Actions) + Checkstyle/SpotBugs** — `./gradlew build` в CI на каждый push.

## 6. Порядок работы, который я бы советовал

1. П. 2.2–2.4 (баги) — полвечера, но именно из-за них проект «не работает на демо».
   П. 2.1 — косметика/устойчивость, делать заодно.
2. Уровень A (иконки, undo, очистка, тесты).
3. Уровень B, начиная с **выделения и перетаскивания** — без них редактор ощущается игрушкой.
4. Уровень C — в зависимости от времени до защиты.

Подкрепляйте каждый пункт ссылкой на лекцию (UML-диаграмма классов и
диаграмма последовательности для undo обязательны в пояснительной записке):
тогда добавление фичи читается как применение теории, а не как «ещё одна кнопка».
